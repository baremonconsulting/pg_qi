## T3 — fail-closed classifier prototype

The prototype is implemented in `src/qi_classify.c` with its public internal
contract in `src/include/pg_qi/qi_classify.h`.

- Input is the analysed PostgreSQL `Query` tree.
- Default behavior is ineligible.
- Supported nodes, built-in operators and aggregates are positively listed.
- Operators and aggregates are checked by catalog OID, namespace, name and
  operand/result types.
- Unsupported nodes, types, relations, joins, operators and aggregates receive
  stable reason codes.
- Inner joins require integer equality keys from different relations.
- Integer division, numeric, floating point, timestamptz, regex, text joins,
  user functions, subqueries and unknown nodes are rejected.
- The classifier does not read or change delegation-frame state.
- Test-only GUCs expose the last completed outer classification for the corpus;
  they are absent from the production build.
- A synthetic contract test proves fail-closed handling of an unknown AST node,
  an invalid operator OID and a null query.

The classifier is not connected to a production routing decision in WP14.2.

## T4 — differential corpus

The versioned corpus contains 15 curated allow-list pairs covering filters,
nulls, boolean expressions, grouping, count/min/max over the approved types,
empty input, duplicates, boundary values, ORDER BY/LIMIT, an integer equi-join
and integer arithmetic. It also executes 100 deterministic fixed-seed fuzz
pairs. The harness compares row count, column type OIDs, textual values and
NULL representation; unordered results are canonicalised. A deliberate
negative control proves that unequal outputs are detected.

Azure PG16 and PG19 results: **230/230 eligible pairs PASS** (115 on each
major), zero value or type divergences, and every pair produced an
authoritative `DuckDBScan`. This covers both PostgreSQL GUC integration paths.

Known issue result on pg_duckdb 1.2.0:
